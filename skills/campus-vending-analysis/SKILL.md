# 校园售货机销售提升分析

## 一句话目标

**找出销售提升点**，不是把数据摆出来。每一段分析必须回答：哪里低于预期／低于上期／低于其他分组 → 最可能的原因（写成"假设"）→ 可落地的动作（具体到机器、时段、品类、楼栋）。只描述现象的段落一律不合格。

## 执行顺序（七步，不可跳步）

| 步 | 命令 | 作用 | 退出码 |
|---|---|---|---|
| 0 | `python scripts/run.py deps` | 检查 Python 依赖（openpyxl 必需，python-docx/matplotlib 可选） | 0 齐全 / 2 缺库（载荷含 `install_command`） |
| 1 | `python scripts/run.py preflight --sales 明细 --categories 分类表 --dorm 人数表 --machine-map 机楼映射 --out out` | 读入体检 + 生成待确认问题 | 0 可继续 / 3 必须停下问人 / 2 输入有问题 |

| 3 | `python scripts/run.py analyze --config ... --out out --period-kind weekly --period-key 2026-W45 --data-root <数据根>` | 清洗 + 六模块 + 环比 + 校验 + 增长点 + 三份报告 | 0 成功 / 4 未确认 / 5 校验未过 / 6 导出失败 / 7 归档已存在需确认 |

**缺依赖怎么办（不要在报错上猜）**：任何子命令开跑前会先自检依赖，缺库时返回
`{"status": "MISSING_DEPENDENCIES", "install_command": "...", "agent_instruction": "..."}`，退出码 2。
正确处置是**原样执行载荷里的 `install_command`**（或 `install_command_all` 装全套），装完重跑同一条命令；
不要跳过依赖继续分析，也不要自行改写安装命令装别的包。只缺 `python-docx` / `matplotlib` 时不中断：
Excel 与 HTML 照常产出，Word 跳过并在 `outputs.docx_error` 说明原因。

**周期键**：周报 `2026-W45`（ISO 周，周一到周日）；月报 `2026-11`（自然月）。给了 `--period-key` 就自动装载上期归档算环比并写本期归档；不给则环比全 N/A。表头一律显示周期键，不用 preflight 猜的时间段标签。

**数据根目录**：由 preflight 的 `Q0_archive_root` 向用户确认一次并写进 `config.archive_root`，之后每期沿用；`--data-root` 只用于临时覆盖。确认后不要更换根目录，否则环比断档。

**退出码 7 = 必须先问人**：本期归档已存在时 `analyze` 会停在退出码 7，**不得**自行加 `--force` 重跑。必须把"本期已有归档，是否覆盖（旧文件另存 .bak）"原样问用户，得到明确同意后才带 `--force`。

## 六个模块（每个都要"校验 + 诊断"）

1. **核心数据项**：11 指标（销售额、在校人数、消费人数、用户消费率、订单数、商品销售数量、连带率、件单价、客单价、人均消费、用户周频次）× 上期/本期/变化额/变化率。校验：本期销售额 = 分析口径合计；订单数必须来自去重订单标识，**禁止用行数代替**；两期天数不同必须只用变化率比较。
2. **时点分析**：0–23 点 24 桶（24:00 归入 00 桶），销量/销售额/用户数。校验：24 桶之和 = 总量；零销售时段保留为 0，不删行。
3. **价格带分析**：默认档位 0–3 / 3–5 / 5–8 / 8 元以上（与成品表模板一致，超出高档自动进溢出档）。档位区间固定「左闭右开」`[下限, 上限)`：**3.00 元计入 3–5 元档**，所以第一档不能叫「≤3 元」；要让 3.00 元留在第一档，把上界改成 3.01，而不是改标签。校验：各档销售额之和 = 总额；占比合计 = 100%（±0.1pp）；件单价无法计算的记录单列不丢。
4. **商品品类分析**：按分类表聚合，未匹配商品单列「未分类」。校验：各品类之和 = 总额；占比合计 100%；单品数按合并后单品计。
5. **机组效能**：左右门按机器编号合并。校验：各机组销售额之和 = 总额；占比合计 100%。
6. **用户习惯**：楼栋×新老生；**渗透率 = 该楼栋消费用户数 ÷ 该楼栋住宿人数**（成品表里列名叫"用户数占比"，就是渗透率）；人均消费 = 楼栋销售额 ÷ 住宿人数。校验：各楼栋金额之和 = 总额；零消费楼栋保留并标注；人数表未覆盖的行显示 N/A 不估算。
   - 老生/新生/新生占比读人数表的「老生人数/新生人数」列，缺失才是 N/A。
   - **性别**优先取人数表「性别」列；没有就按该楼栋机组的男/女类型推断，并在「12_口径与溯源」注明是推断。
   - **楼栋组**（如"十栋+十一栋"）的合并只按人数表自己的写法生效（`+ / 、 ,` 为分隔符），程序不猜测任何合并。

## 时点噪声闸门（防止把噪声当问题）

一周两千单时，00:00 只有几单，在这种样本上证伪"跌 15%"只会产出假问题。因此：

- 单小时判断要求上期该时段成交 ≥ 15 笔，且金额影响 ≥ max(60 元, 本期总额 0.5%)。
- 样本不足时把相邻 2–3 小时合并成窗口判断（上期成交 ≥ 30 笔、影响 ≥ 总额 0.8%），文字里必须写明"单小时样本不足，按窗口合并"。
- 时点类建议最多 3 条，按金额影响排序。**表格仍然 24 行全保留**，闸门只作用于建议清单。

## 三条诊断禁令（代码强制，不是提示词）

1. `evidence` 为空的建议 → 直接丢弃，不进清单。
2. 原因只能写"原因假设：…"，写成结论即校验 FAIL。
3. 动作必须含责任对象（哪台机器/哪个时段/哪个品类/哪栋楼）+ 预期效果（可量化）+ 验证方式（看哪个指标、下期比什么、门槛）。模块解读必须同时含 `【问题】【假设】【动作】` 三段，否则 `CHK-TXT-*` FAIL。
4. **责任对象**单独成列（`13_销售提升点清单` 的「责任对象」），由模块固定映射生成：核心→运营负责人、时点→运维值班责任人、价格带→商品定价责任人、品类→采购补货责任人、机组→运维补货责任人、楼栋→楼栋运营责任人，格式为「角色（具体对象）」，脚本自检 `每条写清责任对象（角色+具体对象）` 兜底。

## 全局校验纪律（硬约束）

- 任何分组表合计 = 顶层总额；无法归属的记录单列并写明差额，**不得静默隐藏**。
- 缺失值一律 N/A 并注明原因；不得用 0、上期值或"大约"填充。
- 部分期间不对比完整期间：天数不同必须注明天数或改用变化率。
- 单品计数可逐条追溯：`10_单品追溯` 列出单品 → 合并的原始名 → 行数。
- 每条动作都要能回指某个表格里的具体数字；给不出证据就不写。

## 样式模板规则

`assets/template.xlsx` 是**格式唯一权威**（表头底色 `#534AB7`、微软雅黑、细边框、列宽、冻结行）。优先级：① 用户明文规格（金额千分位两位小数、占比两位小数、环比正负红绿）② 模板实测样式 ③ 内置默认。模板缺失 → 用内置默认并在「00_说明」写"样式来源：内置默认（原因）"，**不报错退出**。环比红绿用条件格式规则实现（改数颜色跟着变）。
